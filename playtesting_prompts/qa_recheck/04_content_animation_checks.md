# QA-Recheck 04 — Content, Maps & Animation checks (assets side)

Companion to `01_mission_and_build.md` … `03_report_format.md`. This is the
**content / maps / animation / assets** slice of the guide: what exists to look
at, how to reach it, and the visual checks a headless gate structurally cannot
cover. Facts are cited to their source topic/commit, not copied.

**Read first:** `docs/SYSTEM_DESIGN_RULES.md` §4 — `render()` returns
immediately when `game.headless` is set, so **no headless gate in this repo can
see a visual defect.** Everything below needs a real window and human eyes.
The unproven list lives in `docs/PENDING_VERIFICATION.md`.

## 1. What exists to look at, and how to reach it

### Maps + map select (feature F8)

- **Reach it in-game:** Main menu → **Solo** or **Host Co-op** → `ENTER` opens the
  **Map Select** screen (`GAME_STATE_MAP_SELECT`). Controls: `W`/`S` or ↑/↓ move
  the list, `ENTER`/`SPACE` play, `ESC`/`B` back out. The highlighted map shows a
  mini-map preview + its theme/size (`src/ui/menu.c`, `map_select_update`).
  **Join Co-op skips the picker** — the host's map wins and arrives in the HELLO.
- **Reach it from the CLI:** `--map=<n>` presets the map index (host then sends it
  in the HELLO; `src/main.c` `parse_args`, applied after `init()`).

Registry (`src/world/map_registry.c` → `assets/maps/*.map`):

| `--map=` | Name | Size (tiles) | Theme | File |
|---|---|---|---|---|
| 0 | Grassland | 46x34 | GRASSLAND | `maps/grassland.map` |
| 1 | Desert | 60x52 | DESERT | `maps/desert.map` |
| 2 | Snow | 34x34 | SNOW | `maps/snow.map` |
| 3 | City | 50x60 | CITY | `maps/city.map` |

Plan/rationale: `docs/ASSET_MAP_PLAN.md` (themes, ASCII `.map` chars
`.`/`#`/`~`/`+`/`S`, spawn marker).

> **Headless blind spot:** headless runs deliberately keep the **fixed classic
> 50x50 world** (`world_init`), never a map file (`AGENTS.md`). So *map
> selection, map size, themes and previews are only observable in a GUI run.* If
> QA only runs `--headless`, the entire map system is untested.

### Textures / assets

- Generated by `tools/gen_assets.py`; `python3 tools/gen_assets.py --verify`
  reports **33 textures** and must leave `git status` clean (`docs/ASSET_MAP_PLAN.md`,
  `docs/EXTENDING.md`). 9 are entity art: `player, zombie, bullet, grenade,
  rocket, medkit, ammo, speed, sword_blade` under `assets/textures/entities/`.
- Zombie size + colour variants and pickup subtypes are part of the theme
  (`docs/ASSET_MAP_PLAN.md` §Themes; unreplicated-vs-mis-rendered history is
  B20/B21 in `docs/BUGS.md`).

## 2. Expected on-screen results

### 2a. R13-I5 — the client renders **sprites, not dots** (the headline check)

Status in `docs/PENDING_VERIFICATION.md`: **FIXED in code (`f7c44f3`), UNPROVEN
on screen.** Host transmits appearance (`art`, `size_q`, `tint[3]`) and the client
reproduces it instead of guessing. See `docs/I5_FIX.md` and
`knowledge/i5-unverified-on-screen.md`.

Two windows, then check (from `docs/PENDING_VERIFICATION.md`, §R13-I5):

1. All entity kinds draw as **sprites on the client, not circles**.
2. A client's zombie matches the host's for the same zombie — **size variation
   and per-variant colour**.
3. The three **pickup types look different** (medkit / ammo / speed).
4. The client's **own character is a sprite in its slot colour**.
5. Client sprite **sizes match the host's pixel-for-pixel** at the same zoom.

A failure here is the exact defect that survived nine commits because no gate can
see it. Treat any dot/circle as a **Major** finding with a screenshot or a precise
description.

### 2b. Animation is **NOT implemented yet** — do not expect motion

- **B31 is retracted** (`docs/BUGS.md`): `COMP_ANIMATION` is never attached and
  `current_frame` is never read, so **nothing animates on either side**. There is
  no walk-cycle, no hurt-flash, no bobbing pickup to test.
- The animation feature (F15) and its Phase D client work are **planned, not
  built** (`knowledge/animation-plan.md`); Phase D is hard-blocked on the I5
  human check. Swords (B40) are in scope for that later stage, not now.
- **Do not file "zombies don't animate" as a bug** — it is the documented current
  state. What you *do* verify now is that static sprites render correctly (2a).

## 3. Visual / HUD checks a headless gate cannot cover

All from `docs/PENDING_VERIFICATION.md` — values are *proven to arrive* headlessly,
never *proven to be drawn*. One human two-window run each. Group them with the
animation checks above in your S5-5 pass:

- **M5-GUI** — guest runs `--ai=bot`; its bot must aim and shoot at host-spawned
  zombies (behaviour, not just the mirror clock).
- **M6** — host's avatar is readable as a character on the client, with its beacon
  **under** the sprite, not over it (R13-I2a/I2b).
- **M7** — dropped-item bullets render and clear on pickup (R13-I3).
- **M8** — host `ESC` freezes the guest and shows "Paused by host"; a second `ESC`
  shows "Host resumed". Launch the host **with** `--events`.
- **N3/N4 HUD** — client HP bar moves with host damage; points/ammo/weapon update;
  wave panel shows real wave/count/"Next wave in Xs"; Kills/Score match; respawn
  countdown appears; beacons sit where the host's do; zombie health bars stay
  inside their background at wave 3+; dead/eliminated overlay matches the mode.
- **B32-B35 (UI audit)** — a client that dies shows respawn countdown or
  `ELIMINATED` (not an empty HUD); single-player no longer shows the multi death
  overlay; the name tag shows your own name in your own colour (`--name=Guest` in
  slot-1 colour); the name tag no longer overlaps the zombie counter.
- **N5 co-op shop (B30/B33)** — client shop prices/balance come from the host and
  move when the host earns/spends; buying on the client raises both sides;
  unaffordable buys show "not enough points" and spend nothing; rockets before
  launcher say "requires another item first".

## 4. Multiplayer refusal — asset mismatch (N2)

Different builds must fail politely, not silently:

- Client on a different `NET_ASSET_VERSION` shows on the **main menu**:
  `Different game art (host N, you M). Both players need the same build.`
- It must not overflow the menu box or overlap the buttons.
- Host console shows `NET: refused peer ... reason=asset mismatch`
  (`src/net/net_client.c`, `src/net/net_server.c`; `NET_REJECT_ASSET`).
- A full server (2 players, a 3rd joins) still refuses politely.

Rationale and the "appends bump the asset version, not the wire" distinction:
`knowledge/versioning-decisions.md`.

## 5. Two-window launch recipe

From `AGENTS.md` — **build and run the branch under test**, not `main`
(knowledge/docs-system.md, human-gate caveat). GUI runs must be detached or the
shell hangs on the window.

```bash
R=<the worktree/branch under test>
cd "$R/build"
IP=$(hostname -I | awk '{print $1}')
setsid ./open_world_zombie_waves --host --port=5123 --name=Host --map=1 \
  >/tmp/opencode/coop_host.log 2>&1 </dev/null &
sleep 2
setsid ./open_world_zombie_waves --join=$IP:5123 --name=Guest \
  >/tmp/opencode/coop_join.log 2>&1 </dev/null &
```

Use `--map=1` (Desert, a non-default size) on the host to also exercise "the
host's map wins" — the guest must load Desert without touching its own picker.
To stop them, use explicit PIDs or `pgrep -f ... | xargs -r kill`; **never**
`pkill -f open_world_zombie_waves` (it matches the shell running the command).

## 6. Reporting

Use the same template and severity taxonomy as `03_report_format.md`; write
`findings/R<n>_*.md` + `SUMMARY.md`. For this slice the fail-the-blocker outcomes
are: **any client dot/circle where a sprite is expected (I5 regression)**, a map
that fails to load or loads the wrong size/theme, and an asset-mismatch that
fails silently instead of refusing legibly. Remember: a green headless gate is
**not** evidence for any check in this file.
